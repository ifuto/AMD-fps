# 21 — 新規 FPS 向上技術の調査（数百件規模）

**このノートは既存実装の整理ではない。** 新たに調査して見つけた、
まだこのリポジトリに無い技術の集合。各項目に出典と、判明している数値を付ける。
数値の無い項目は「未測定」であり、**導入前に必ず測定する**（前提条件: 論文の高速化を
Minecraft に無測定で移植しない）。

---

## 1. メッシュ生成（最大の CPU コスト）

### 1-1. Greedy meshing（隣接 quad の統合）
- 出典: 0fps.net "Meshing in a Minecraft Game"
- **実測: naive 6634 quad / 26536 頂点 → greedy 1983 quad / 7932 頂点（3.3×）**
- 理論: 最適メッシュの **8 倍以下**であることが証明されている。球状ジオメトリでは
  典型的に **O(√n) 倍小さい**
- **3 スイープで十分**（6 方向ではなく 3 平面）
- ハッシュマップではなく**事前確保マスクバッファ**を使い、メッシュ後にボクセルをゼロ化
- 限界: 曲率と連結成分が増えると効果が落ちる（スライスごとのエッジ数が増えるため）。
  孤立した単一立方体の集合では naive と同一

### 1-2. Monotone meshing
- 同出典。**実測 4306 三角形 vs greedy 1983 quad** → greedy が勝利
- 三角形出力は quad 出力より約 30% 遅い（それだけで説明できる差がある）

### 1-3. 近傍チャンクを含む 1 ブロックのパディング境界
- 出典: minicraft PR #3
- 境界に**はみ出し面が出なくなる**。編集時は「編集された境界面を共有する近傍」だけ再メッシュ

### 1-4. テクスチャ配列（atlas ではなく DataArrayTexture）
- 出典: 同上。面ごとに layer インデックス、atlas のブリーディングが無い
- 別の出典（GameDev.net）も「atlas か texture array でテクスチャ切替を減らせ」とする

### 1-5. 面をテクスチャでソート
- 出典: GameDev.net voxel batching
- **同じテクスチャの面を同じ VBO に集める**と `glDrawRangeElements` のスパン数が減る
- ドローは**シェーダ→頂点バッファ→テクスチャの順でソート**（状態変更が最も高コスト）

### 1-6. ワールド座標への事前変換
- 出典: 同上。**メッシュ生成時にワールド座標へ変換**しておけば頂点シェーダでやらなくて済む

### 1-7. 16³ の小さなセクション
- 出典: 同上。**16×16×128 より 16×16×16 の方が構築が桁違いに速い**し、
  プレイヤーは小さな範囲しか編集しない

### 1-8. 頂点プーリングと 6 方向バケット
- 出典: nickmcd.me "High Performance Voxel Engine"
- greedy meshing と相性が良い（方向ごとにスイープするので、方向ごとにバケットを要求できる）
- **バケットを埋めきらなくてもメッシュ時間・描画時間に影響しない**（実測）ので、
  正確なサイズのバケット管理は不要
- チャンクデータを LOD に基づき**スーパーチャンクへ統合してからメッシュ**するとドローが減る

### 1-9. 近傍が揃ってからメッシュする
- 出典: minicraft PR #3。**in-range の近傍がロードされてから**メッシュし、
  チャンク生成完了時に近傍を再 dirty 化 → シームにはみ出し面が出ない

### 1-10. チャンクを座標キーの Map で持つ
- 出典: 同上。子ノードの走査ではなく Map 参照

### 1-11. ボクセル DDA レイキャスト（Amanatides–Woo）
- 出典: 同上。**全チャンクに対するレイキャストの代わりに**グリッド DDA

## 2. 環境光（AO）とスムーズライティング

### 2-1. 頂点あたり高々 4 種類の AO 値
- 出典: 0fps.net "Ambient occlusion for Minecraft-like worlds"
- 隣接立方体の情報だけで計算でき、**視点非依存**。コストはメッシュ構築時間の僅かな増加

### 2-2. 3 近傍 AO（0〜3）と「2 つの辺が遮蔽されたら 0」
- 出典: minicraft PR #4。**対角の異方性アーティファクトを消す**

### 2-3. 四角形の対角を「暗い角の組」を通るように反転
- 同出典。**AO の異方性が消える**。実装コストほぼゼロで見た目だけ良くなる

### 2-4. greedy 統合の条件に AO／スカイ／ブロックのマスク一致を含める
- 同出典。これを忘れると統合後の quad で光が壊れる

### 2-5. 角 AO には対角近傍も必要
- 同出典。3×3 近傍は**対角を含む**（9 チャンク）

### 2-6. スカイライトは上から下への単一カラムパス
- 出典: GameDev SE "voxel-based lighting"
- **再帰もリストもデータ構造も不要。1 パスで終わる**。トーチ等は後段で加算
- フラッドフィルを使うのは非自明な場合だけ

### 2-7. 境界を 15 ブロック以上取る
- 出典: minicraft PR #4。**近傍チャンク内の光源が厳密に解決できる**。
  未ロードの近傍は「完全にスカイライトされた空気」として読み、ロード時に再点灯
- 実測: 16×32 チャンクで**光 約 10ms ＋ メッシュ 約 25ms**（Node 環境）

### 2-8. MC の光カーブ `brightness(l) = l / (4 - 3l)`
- 同出典。線形ではない

### 2-9. コーナーシェーディングは 1/4 レベル精度
- 同出典。**面の外側で角に接する非不透明でない ≤4 セルの平均**

## 3. オクルージョンカリング

### 3-1. ラスターオクルージョンは Hi-Z より正確で速い
- 出典: nvidia-occlusion-culling-demo の実測
- **Hi-Z: GL 11051／CPU 10921（34% 可視）**
- **Raster: GL 4919／CPU 4820（12% 可視）** — **2.2 倍**
- バウンディングボックスを**色書き込み無効で「見えないまま」ラスタライズ**し、
  深度テストを通ったフラグメントが可視を示す
- 向きと寸法がより正確に表現されるため Hi-Z より良い結果になる

### 3-2. 時間的コヒーレンス（前フレームの結果を使う）
- 同出典。**前フレーム可視だったものを先に描く → 深度バッファを準備 → 可視性をテスト →
  まだ描いていない可視物を描く**。オブジェクトごとの描画回数が 2 回ではなく**ちょうど 1 回**
- 欠点: 動きのある場面でアーティファクト。現在フレームのデータと両立させれば回避できる

### 3-3. 深度バッファの再投影
- 出典: gamesindustry.biz "Overview on popular occlusion culling techniques"
- 前フレームの深度を現在のフレームへ再投影し、それにボックスをソフトウェアラスタライズ

### 3-4. Intel Masked Software Occlusion Culling（最重要の新規項）
- 出典: Intel MOC 論文／スライド
- **全ジオメトリを software culling に通してもシングルコアで CPU 4ms**
- **フル解像度深度バッファ方式がカリングする三角形の 98% をカリングしつつ、従来比 3 倍速い**
- **32×8 タイルで 256 ピクセルを並列**（AVX2 の 8-wide × 32bit）
- **8×4 サブタイルごとに 2 つの float 深度 ＋ 32bit マスク**を保持し、
  **4×2 タイルぶんを SoA で持って 8 タイルを並列に深度テスト**
- **オクルーダのラスタライズとオクルージョンクエリをペナルティなしにインターリーブ**できる
  → シーングラフ走査にそのまま組み込める
- **描画順ソート（前→後）がオクルージョンカリングエンジンでよく効く**
- 「working layer 破棄ヒューリスティック」: 既に遮蔽済みのタイルはカバレッジテストを飛ばす
- **SSE2 → AVX2 で 5 倍**
- Hi-Z 生成の合計時間は**約 1ms**
- バッファのマージコストは 640×400 で **0.9%**、1080p で **4.4%**（無視できる）
- AMD での注意: Intel 実装は SIMD 前提。**AMD CPU でも AVX2 は動く**が、
  レーン幅とスループットは実測が必要

### 3-5. Umbra 方式のポータルとセル
- 出典: 同上。**オフラインでボクセル化しポータルとセルの空間データベースを作る**。
  実行時は低解像度の階層深度バッファを最適化されたソフトウェアラスタライザで生成

## 4. 即時モード描画（ImmediatelyFast が押さえている領域）

### 4-1. 看板テキストのバッファリング
- 出典: ImmediatelyFast `experimental_sign_text_buffering`
- **毎フレーム再描画するのではなくテキストをバッファに保持**
- 実測: 看板 200 枚で **70→125 FPS（1.79×）**、+Sodium で **110→300（2.73×）**

### 4-2. 地図テクスチャのアトラス化
- 同 `map_atlas_generation`。**複数の地図テクスチャを 1 枚にまとめる**

### 4-3. フレームバッファ切替の削減
- 同 `avoid_redundant_framebuffer_switching`
- **ワールド内の多数の異種描画（エンティティ・パーティクル・ブロックエンティティ）や HUD で
  FB 切替を減らす**

### 4-4. テキスト描画のデータキャッシュ
- 同 `fast_text_lookup`。**文字を描画する間のデータをキャッシュ**

### 4-5. フォントアトラスの拡大
- 同 `font_atlas_resizing`。高解像度・カスタムフォント向け

### 4-6. ブロックエンティティ描画
- 実測: **チェスト 400 個で 170→205（1.20×）**、+Sodium で **315→410（1.30×）**

### 4-7. ブロックエンティティレンダラの距離カリング
- 出典: Optimum issue #84。**エンジンが無視している RenderRange で距離カリングする**

### 4-8. アニメーションするブロックエンティティのフラスタムカリング
- 同出典。**オフスクリーン時にシェーダ・ユニフォーム・ドローの仕事を丸ごと飛ばす**

### 4-9. スロットごとの描画情報を使い回す
- 同出典。**1 可視スロットあたり約 104 バイト／フレーム、インベントリを開くと約 14KB／フレーム**
  の確保を、スレッドごとのスクラッチで使い回す
- **これはドロー数削減ではなく確保削減**。区別が重要

### 4-10. 重要な教訓
- 同出典: 「**batch the draw calls という枠組みは既に処理済み**のことが多い。
  本当に空いている勝ち筋は確保削減とカリング」
- **GUI/HUD のドローバッチ化（実測 81%）は調査されたが却下された** —
  GUI Mod がパッチする層でしかできず、効果と Mod 安全性を両立できないため

## 5. メモリ（FerriteCore／ModernFix が押さえている領域）

### 5-1. ブロック状態のプロパティを上位構造から読み出す
- 出典: FerriteCore。**各状態が独自のプロパティ Map を持つのをやめ、上位構造から読む**

### 5-2. 衝突・描画形状の共有インスタンス化
- 同。**膨大な数のブロックが同一形状を共有しているので、重複を 1 インスタンスへ向ける**

### 5-3. 空のデータコンポーネント Map のオーバーヘッド除去
- 同。**空でも Map はメモリを食う**

### 5-4. モデル系の重複排除（歴史的に最大級）
- 同。**multipart モデル述語・モデルインスタンス・ResourceLocation 文字列・
  baked quad 頂点データの重複排除**。単体で数百 MB
- 注意: **MC 1.21.5 でモデル系が全面書き換えされ FerriteCore 8.0.0 で一時削除された**。
  1.21.11 では**再実装の余地がある**（＝競合相手がいない領域）

### 5-5. 未使用リソースの動的解放
- 出典: ModernFix。**セッション中に使っていないリソースを動的に解放**。
  長時間セッションでヒープが右肩上がりになるのを防ぐ

### 5-6. 実測値
- **All Of Fabric 3: ヒープ 1792MB → 984MB（約 45%、800MB 削減）**

### 5-7. RAM ≠ FPS
- 出典: FerriteCore 公式の説明
- **ヒープを増やすと GC の停止が長くなる**。小さくすると GC が減り短くなり、スタッタが消える
- ライブデータが多いほど GC は頻繁に、そして長くなる

### 5-8. 参照カウント 1 でのアンロード
- 出典: ゲームエンジン一般。**キャッシュだけが保持している（use_count == 1）ものを消す**

## 7. Vulkan／GPU 送出

### 7-1. 送出と待機
- **vkQueueSubmit の完了を待たない** — 次フレームの準備を続ける（直列化の回避）
- **少量の GPU 作業を送出しない** — GPU が遊ぶ
- **数ドローだけの小さなコマンドバッファを記録しない**
- **vkQueueSubmit の回数を最小化**（1 回ごとに CPU コストが大きい）
- **送出・プレゼン中に CPU を遊ばせない**
- **タイムラインセマフォでフェンスなしのフレームペーシング**

### 7-2. パイプライン
- **vkCmdBindPipeline を最小化**（CPU・GPU 両方にコスト）
- **specialization constant は命令数とレジスタ数を減らす**ことがある
- **specialization constant はオフラインのシェーダ順列の代わりになり、
  同梱するバイトコードを減らせる**
- パイプラインキャッシュと非同期生成
- **変わらない動的状態を PSO で有効にしない**

### 7-3. ディスクリプタ
- **ディスクリプタセットの binding の隙間は GPU メモリの無駄**
- **ステージフラグを ALL にしない**（最小限に）
- **bindless／descriptor indexing** — 巨大な 1 セットをシェーダ内で索引。
  **CPU オーバーヘッドが極端に減り、バインドコストもほぼ消える**
- **update-after-bind** で使用中のセットを更新できる（使用中のディスクリプタに触れなければ）
- **VK_EXT_descriptor_buffer** — ディスクリプタをバッファに置き、CPU ポインタへマップして
  メモリ書き込みだけで更新。**ディスクリプタ更新の API 呼び出しが完全に消える**
- コスト: **ディスクリプタセット 1 DWORD／動的バッファ 2 DWORD（robust access ON で 4）／
  push constant は 4 バイトごとに 1 DWORD**

### 7-4. AMD 固有の非同期コンピュート
- **export bound シェーダとの並列実行では非同期コンピュートの性能が悪い**
- **非同期で走らせるなら小さいワークグループ（64）の方が良い**
- **小さいディスパッチは async より pipelined compute の方が良い**
- **大きいディスパッチの後に大きいドロー、も pipelined compute が向く**
- 同一キュー内はセマフォ／フェンス不要、バリアで同期する

## 9. 次に実装する順（数値が大きく、結線が浅いものから）

1. **2-3 対角フリップと 2-2 の 3 近傍 AO** — ほぼゼロコストで見た目が正しくなる
2. **1-1 greedy meshing** — 3.3× の quad 削減。既存のメッシャに追加できる
3. **4-7・4-8 ブロックエンティティの距離・フラスタムカリング** — 既存のカリング部品が使える
4. **4-1 看板テキストのバッファリング** — 2.73×（+Sodium 時）
5. **3-1・3-2 ラスターオクルージョン＋時間的コヒーレンス** — Hi-Z の 2.2 倍
6. **3-4 Intel MOC 方式の SIMD ソフトウェアカリング** — 4ms で 98% カリング
7. **5-1〜5-4 FerriteCore 系メモリ** — 1.21.11 ではモデル系が**空白地帯**
8. **1-3〜1-11 メッシュ生成の周辺最適化**
9. **6 系 CPU キャッシュ** — 各所で横断的に（特に 35 バイト制限とホット/コールド分割）
10. **7 系 Vulkan** — レンダラ着手と同時に

**各項目の完了条件**: ゲーム実行中に呼ばれ、オーバーレイか `/amdfaster stats` で
効果が見えること。「テストが通った」では完了としない。
