# 14. Stage 8〜11 — Minecraft 適応層、頂点単位のライト、ブロックシェーダ

対象コミット範囲: `d5b8258`（`net.amdfaster.mc`）→ `1de071e`（block シェーダ）。
CI run `37762531498` で緑。

---

## 1. なぜ「Minecraft 型に触るファイル」を 1 つに絞ったのか

`net.amdfaster.mc` 以外に `net.minecraft` を import するファイルは `AmdFasterCommand` だけ
（`grep -rl "net.minecraft" src/main/java` で確認）。これは意図的な構造で、理由が 2 つある。

**テスト可能性。** メッシャ、ライティング、メッシュフォーマット、GPU レイアウトはすべて
Minecraft なしで動く。実行中のクライアントが要らないので CI で回る。`LevelBlockSampler` が
`BlockState` を **int に落としてから**下流に渡すので、下流は `BlockState` を知らない。

**ライセンス境界の明確化。** Sodium は PolyForm Shield 1.0.0 で、ソースからの派生が禁止。
参照してよいのは「振る舞い」であって「コード」ではない（ユーザ指示: 同一機能の独立実装は可、
ソースの複製は不可）。Minecraft 型に触る面が狭いほど、その境界を主張しやすい。

### 1.1 `BlockFaceSource` を all-int にした理由

```java
int spriteId(int x, int y, int z, int axis, int face);
int tint(...); boolean isCutout(...); int blockLight(...); int skyLight(...);
```

`BlockState` を渡さない。合成（sprite + tint + cutout + light）を **fake で組める**ようにする
ためで、これで `LevelBlockSampler.key()` がテスト可能になった。

## 2. `BlockKeys` — マージキーのビット配置

メッシャは「同じ見た目・同じ光り方なら 1 枚に結合してよい」。その同値判定を 1 個の int 比較に
するのが `BlockKeys`。

| bit | 内容 |
| --- | --- |
| 31 | present フラグ（`NO_GEOMETRY = 0`） |
| 17..30 | sprite（14 bit、`MAX_SPRITE = 16383`） |
| 13..16 | block light |
| 9..12 | sky light |
| 5..8 | tint + 1（`NO_TINT = -1`、`MAX_TINT = 14`） |
| 1..4 | emission |
| 0 | cutout |

**範囲外は例外。** sprite を丸めて別 sprite と alias させると、違うテクスチャのブロックが
1 枚に結合されて見た目が変わる。黙って劣化させるより落とす。

`light(key)` は `LightValue.pack` と同じ `(sky << 20) | (block << 4)` を返す。2 つの表現が
別々に存在すると必ずずれるので、片方から導出している。

### 2.1 `SectionCoords` をシフト／マスクで書いた理由

`/` と `%` は **0 方向に切り捨てる**。`-1 / 16 == 0`、`-1 % 16 == -1` なので、
ブロック −1 が「セクション 0 のローカル −1」になる。セクション境界で必ず踏む。
`sectionOf = c >> 4`、`localOf = c & 15` なら負も正しく切り下がる。

## 3. ライトを頂点単位にした（Stage 9）

### 3.1 問題

greedy meshing で結合された quad は複数ブロックをまたぐ。両端が 0 と 15 の明るさの境目にある
ことは普通に起きる。**1 quad に 1 個のライトマップ値**では、広い面が平坦に見える。前段で作った
ライティングエンジンが使えなかったのはこれが理由。

### 3.2 変更

- `Quad` は **16 コンポーネント**になり、`lightA..lightD` を持つ（`cornerX` の番号順）。
- `VertexLight.packLight(light, ao) = (light & 0x00FFFFFF) | (ao << 24)`。
  ライトマップは bit 4..7 と 20..23 しか使わないので **24..25 が空き**。1 個の 4 バイト
  attribute がライトマップと AO の両方を運ぶ。
- ライトは**独立した頂点ストリーム**。理由は 2 つ:
  1. cutout 用の Z pre-pass は位置しか読まない。狭いライトストリームならコスト 0。
  2. ライトはジオメトリが変わらなくても変わる（松明を置く、日が暮れる）。そのとき書き換わる
     のはこのストリームだけで済む。interleave すると 1 頂点 1 ワードのためにセクション全体の
     頂点データを書き直すことになる。
  3. おまけに 4 バイトは 64 バイトのキャッシュラインを割り切る（16 頂点/ライン、またぎなし）。

### 3.3 この変更で踏みかけた地雷 — 頂点 dedup キー

`MeshletBuilder.VertexKey` は元々 `(x, y, z, u, v)`。**位置も uv も同じでライトだけ違う**角が
存在する — 明るい面と暗い面の境目がまさにそれ。ここで結合すると、メッシャが**先に訪れた方**の
ライトを両方が継承し、継ぎ目の見た目が走査順に依存する。

→ `light` をキーの 6 番目の要素に追加。両方向をテストで固定:
同一の角は今までどおり結合する / ライトだけ違う角は結合しない。

### 3.4 `.comp` シェーダは無変更

`grep` で確認: 参照しているのは meshlet あたりのインデックス数 `372` と頂点数 `248` のみで、
4 本目のストリームに影響されない。

### 3.5 アップロードレイアウト

`MeshUploadLayout` は **4 リージョン**（positions → attributes → **lights** → indices）。
1 回の逐次パスでステージングバッファを埋められる順序を保つ。
オフセットは**別実装で再計算して差分を取ってから**書いた（手計算の期待値は過去 10 回以上外している）。

## 4. メッシュ生成時にスムースライティングを計算する（Stage 10）

`SectionMesher.meshSmooth` はセクションにつき `LightCache` を 1 回埋め、面ごとに 4 角を導出。
キャッシュの意味がここに出る: スムースライティングは 1 角あたり 4 サンプルを要求するので、
level から直接引くとライティングがメッシュ生成の主コストになる。

### 4.1 角の対応表 — いちばん壊れやすい場所

`SmoothLight.face` の角の番号は `(minU,minV), (maxU,minV), (maxU,maxV), (minU,maxV)`。
`Quad` の角の番号は**巻順**。両者は最初の 2 つが一致し、**後ろの 2 つが入れ替わる**。

```java
private static final int[] SMOOTH_CORNER_ORDER = {0, 3, 1, 2};   // index = cornerA * 2 + cornerB
```

間違えると**すべての面の片方の対角線に沿って照明の継ぎ目**が出る。スクリーンショットでは
見落としやすく、プレイ中は確実に気づく。

**テストは表の中身ではなく不変条件を検証する:** 6 方向 × 4 角すべてについて、選ばれた
smooth index が「その角と同じ (u,v) 端にある index」であることを確認。表の中身を
assert すると、テストが検証対象の複製になり、表と巻順が一緒にずれたとき通り続けてしまう。

全 6 方向 × 4 角を独立実装で照合済み、かつ各方向で全角が 0..3 を過不足なく使う（全単射）ことも
確認した。

### 4.2 遮蔽のテストが 2 つ同時に主張すること

`(3,5,3)` を「光る固体ブロック」にして、その対角にある角を検証する。

1. 遮蔽レベルが 3 → **2** に下がる。
2. block light は **3 のまま上がらない**。

2 が本命。よくある実装は固体サンプルも平均に入れるので、発光ブロックの周囲に明るい縁が出る。
スキップする実装では明るさは変わらず、陰だけ濃くなる。

### 4.3 ジオメトリは動かない

2 つのエントリポイントが「すべての position と uv で一致し、ライトだけで異なる」ことを
固定。ライティングの変更が黙って頂点を動かすと、静止画では見えなくて動きでばれる。

## 5. ブロックシェーダ（Stage 11）

### 5.1 ライトは頂点シェーダで展開する

頂点は 1 回しかシェーディングされないが、そのフラグメントは数百になりうる。
interpolator が運ぶのは小さな float 1 個で、ワード 1 個＋展開をピクセルごとに繰り返すより安い。

### 5.2 `discard` を使わない

`discard` は early depth を無効化する。葉・草・フェンスが大半のシーンでは、省ける分より
失う分が大きい。cutout は **Z pre-pass + depth test `EQUAL`** で処理するので、
このシェーダに届くフラグメントはすべて描かれるもの。

### 5.3 ディスクリプタセット 1 を使う

セット 0 はカリングパイプラインのもので、`STAGE_COMPUTE` のみ宣言している。
グラフィックスシェーダがセット 0 を読むと、そのレイアウトがグラフィックスステージを
名乗らざるをえなくなる。**使わないステージを名乗るレイアウトは検証コストを払うだけ**。

フレームブロックは同じフィールド順で再宣言し、**1 個のバッファを両パイプラインで共用**。
テストが 2 つの宣言を突き合わせる。

### 5.4 `BlockBindings` + `BlockBindingsTest`

binding・頂点フォーマット・push constant・フレームオフセットを Java 側で持ち、
テストが **GLSL ソースを読んで**一致を確認する。

binding の不一致は Vulkan で最悪クラスのバグ: validation が通り、パイプラインが作られ、
そのうえでシェーダが**一致しない binding が指す先のメモリ**を読む。ドライバと
そのとき何が resident だったかに依存して、ちらつき・色違い・無描画のどれかに化ける。

### 5.5 CI が捕まえた実エラー

フォーマット定数を**リテラルで書いて 3 つとも外した**。CI: `expected: <96> but was: <84>`。
VK_FORMAT enum は 8 個ずつの綺麗なブロックになっていない — SRGB バリアントを持たない
コンポーネント幅があるので、グループの長さが不均一で、ある項目の位置はそれ以前の
全グループに依存する。

→ `VK10` を直接参照。リテラルにした理由は「LWJGL なしでこのクラスを使えるようにする」だったが、
それは価値がなかった（LWJGL は元々コンパイルクラスパスにあり、`VkContext` は `VK10` を
import している）。**ずれようがない定数 > ずれうる定数**。

同時にテストも強くした: `BlockBindings` を `VK10` と比べるのは、両側が同じ定数を
名指しする以上トートロジーになる。代わりに **GLSL の入力型を読み、`Meshlet` の stride を
コンポーネント数で割り、それを保持できる唯一のフォーマットを導出**して比較する。
これは実際に GPU フォールトを起こす誤り（stride とフォーマットのサイズ不一致）と、
符号や 3 コンポーネント版への取り違えを捕まえる。

## 6. この段階で学んだこと（次回への引き継ぎ）

- **`grep` はファイル名を指定せずツリー全体にかける。** 13 個の呼び出し箇所を書き換えたとき、
  テストファイル名を列挙して grep したため `SectionMeshBuilderTest` を取りこぼし、CI で落ちた。
- **置換は機械的にやると巻き添えが出る。** 同じ置換が、正しく 16 引数で呼んでいた 1 箇所まで
  13 引数に書き換えた。置換後に対象を目視する。
- **rebase が「both added」を大量に出したら偽衝突を疑う。** このリポジトリは **shallow clone** で、
  graft 点がマージベースになって全ファイルが衝突する。復旧は
  `git rebase --abort` → `git fetch` → `git reset FETCH_HEAD` → `git add -A` → 再コミット。
  作業ツリーの内容は正しいので、origin との差分が意図したファイルだけであることを確認してから。
- **手計算の期待値は信用しない。Python で別実装して差分を取る。** ただし表示側の取り違えにも
  注意 — ライトの block は bit 4..7 なので `l & 0xF` では常に 0 になり、モデルが壊れたように見えた。
- **アサートしていないテストを書かない。** `VK_API_VERSION_1_2 & 0 == 0` は恒真で、
  何も検証していなかった。書いてから自分で消した。
