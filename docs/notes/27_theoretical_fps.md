# 理論FPS ―― モデルと、そのモデルが信用できる範囲

`docs/model/fps_model.py` が計算本体。`fps_model_output.txt` が出力。
**Minecraftは一度も実行していない。** これは測定ではなくモデルで、
数字の出所を3種類に分けてある。混ぜると意味が無くなる。

| 記号 | 意味 |
| --- | --- |
| `[CODE]` | このリポジトリの定数/テストで確定している算術。CIが緑なので値は保証される |
| `[SRC]` | 外部の実測値。出典を書く |
| `[ASSUM]` | ワークロードの仮定。**唯一の自由パラメータで、全部明示する** |

## 結果

| シナリオ | バニラ | +AMD-Faster | 全Mod入り | Mod+AMD-Faster | **対Mod倍率** |
| --- | --- | --- | --- | --- | --- |
| A 平地を歩く (RD12定常) | 11.12 ms | 6.36 ms | 7.72 ms | 6.36 ms | **1.21×** (130→157 FPS) |
| B 村・洞窟 | 27.80 ms | 11.25 ms | 16.87 ms | 11.25 ms | **1.50×** (59→89 FPS) |
| C TNT×100＋大量パーティクル | 90.30 ms | 16.49 ms | 59.89 ms | 16.49 ms | **3.63×** (17→61 FPS) |

**「全軽量化Mod全入れに単体で勝つ」が目標なので、見るべきは右から2列目ではなく最後。**
バニラ比の 1.75×/2.47×/5.47× は、Sodium と EntityCulling が既に取っている利得を
二重に数えた数字で、目標に対しては意味が無い。

## このモデルに入る前の3つの誤り（直した）

1. **ドローコール1本を 0.02 ms としていた → 0.002 ms。**
   0.02 だと 700 セクションで 14 ms = フレーム予算の全部になり、
   外部実測（vd=8 で 289 draw・フレーム 5.6 ms）と矛盾する。**10倍の過大評価だった。**
2. **名前プレートを全エンティティに掛けていた** → 名前付きの一部だけに。
3. **メッシュ構築をメインスレッドのフレーム時間に足していた** → ワーカープール側。
   バニラの `SectionRenderDispatcher` はワーカースレッドで構築するので、
   平均FPSではなくスタッターに出る。別バケツに分离した。
4. **エンティティtickを毎フレームとしていた** → 20Hz。60FPSなら 1/3。

## 検算

- 視錐台の生存率: `HierarchicalFrustumCuller` の実測 **21.2%** に対し、
  水平FOV 70度の楔は独立計算で **19.4%**。別経路の数字が近いので、
  エンティティに流用しても大きくは外れない。
- 光のみ再構築: メッシュレット 5332 B のうち光 992 B ⇒ **81.40%** のバイトを省く。
- 差分再構築: 16³=4096 セルのうち触るのは 27 ⇒ **99.34%**。
- 爆発: 1352レイ×18ステップ = **24,336 参照 → 823 distinct = 29.6×**。

## このモデルに入っていないもの（＝実際はもっと上振れしうる）

配線されていない、または ms に換算できないため**意図的に除外**:

- **Vulkan バックエンド一式**（occupancy / coalescing / root signature / mesh shader / MDI）
- **HiZ によるエンティティ遮蔽**（深度源が未供給）
- **`FastRandom`** の 4–8×（乱数がフレーム時間の何%かは未測定）
- **false sharing 回避**（5.0×/9.7× は*そのカウンタ*の速度で、フレーム時間ではない）
- **inlining budget / hot-cold split / bytecode size**（JITの挙動で、ms換算できない）
- **GPU側の時間**。バニラが CPU 律速という前提で CPU しかモデル化していない

## 感度（一番効く仮定）

削減不能コスト `other`（GUI・HUD・バニラの残り）は `[ASSUM]` で、
シナリオAでは最適化後フレームの **63%** を占める。ここが結果を支配する。

## 全Mod入り比較で AMD-Faster が実際に足すもの（シナリオB）

| 項目 | 全利得 | 未開拓 | Modの先行率 |
| --- | --- | --- | --- |
| particle（Mod横断の合計予算） | 0.888 ms | **0.755 ms** | 15% |
| mod renderer | 1.811 ms | **0.906 ms** | 50% |
| entity draw | 6.000 ms | 0.900 ms | 85% |
| nameplate | 0.757 ms | **0.681 ms** | 10% |
| entity tick | 1.550 ms | 0.620 ms | 60% |
| sound（適応的カットオフ） | 0.450 ms | **0.450 ms** | **0%** |
| shadow | 1.064 ms | 0.426 ms | 60% |
| orb merge | 0.583 ms | 0.408 ms | 30% |
| blockentity | 2.583 ms | 0.388 ms | 85% |
| draw(terrain) | 0.868 ms | 0.087 ms | **90%** |

**Sodium と EntityCulling が既に取っている所では勝負にならない。**
AMD-Faster が単独で勝てるのは **パーティクルのMod横断予算・音の適応的カットオフ・
名前プレート** で、いずれも既存Modが触っていない領域。
それ以外の大半は AMD/Intel 固有のGPU最適化に懸かっており、**それはまだ動いていない。**

## 結論

- **バニラ比 1.75–5.5×** は理論上出る。ただし目標ではない。
- **全Mod入り比 1.21–3.63×。** 軽いシーンでは 1.2 倍程度で、
  「全Mod入りに単体で勝つ」は**今の配線だけでは達成できていない**。
- 重いシーン（TNT・大量パーティクル）では 3.6 倍で明確に勝つ。
  ユーザーが名指しした TNT は実際に一番効く領域。
- **差を埋めるのは Vulkan バックエンドと HiZ 遮蔽**で、両方まだ動いていない。
