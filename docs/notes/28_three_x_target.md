# 3倍目標 ―― どこから出すか、何が足りないか

`docs/model/frame_split.py` が計算本体。**提示は FPS で行う**（ms では実感できないため）。

## 結論（全Mod入り = Sodium+ImmediatelyFast+EntityCulling+Lithium+FerriteCore+ModernFix 比）

| 状態 | A 平地 | B 村・洞窟 | C TNT×100 |
| --- | --- | --- | --- |
| 今の配線 | 130 → **206 FPS** (1.59×) | 59 → **94** | 17 → **27** |
| 配線可能なものを全部配線 | 130 → **376 FPS** (2.91×) | 59 → **172** | 17 → **49** |

**2.91 倍。3 倍に一歩届かない。** ここから先は assumption を上げて数字を作るのではなく、
足りないものを名指しする。

## 推定の `other` をやめた

前バージョンは「削減不能コスト 4.0 ms」という黒箱を置いていた。これだと
最大 7.72/4.0 = **1.93 倍が数学的上限**で、3 倍は最初から不可能だった。
実プロファイラの内訳に置き換えた:

| 区分 | フレーム占有率 | Mod先行 | AMD全利得 | 配線 |
| --- | --- | --- | --- | --- |
| entities | 21.4% | 85% | 89.4% | 一部 |
| terrain | 13.4% | 90% | 62% | 済 |
| rendertype | 22.4% | 50% | 85% | **未** |
| **gui** | **17.6%** | **0%** | **85%** | **未** |
| tick | 5.3% | 60% | 55% | **未** |
| misc | 19.9% | 20% | 45% | **未** |

**GUI が 17.6% で、対象Modスタックの誰も触っていない。** ここが最大の未開拓。

## 二つの誤りを直した

1. **クラスの javadoc の絶対 ms を信じない。**
   `GuiBatcher` は「200要素 × 0.02 ms = 4 ms/フレーム」と書く。`CloudMeshCache` 2 ms、
   `WeatherMeshCache` 1.2 ms、`AnimatedTextureScheduler` 1.2 ms、`TranslucentSortCache` 0.9 ms。
   **全部足すと 9.3 ms で、シナリオAのフレーム(7.72 ms)を既に超える。**
   0.02 ms/要素は、既に誤りと判明したドローコール単価 0.02 ms と同じ誤りで、
   GL実測（draw 0.41 µs + texbind 0.48 µs /1000回）の約10倍。
   **javadoc からは相対削減率だけを使い、占有率はプロファイラ実測から取る。**

2. **`entities` の Mod先行率 0.85 が二つの別物を混ぜていた。**
   カリング（EntityCulling が取る）とドローコスト（誰も取っていない）は別の軸。
   分けて計算し直した: カリング 78.81% ＋ 残り 21.2% のインスタンス化。

## 3倍に足りないもの（名前を挙げる）

**インスタンス描画を実際に発行するレンダーバックエンド。**
`docs/notes/24` の公表ベンチは **平均 FPS +155%、1% Low +107%**。
同ノート自身が「Rentities の NVIDIA 上の数字で、そのまま期待しない」と警告しているので、
モデルでは 2.0× に減額して使っている（それでも 2.91×）。

現状:
- `shaders/entity_instanced.vsh` / `entity_bones.comp` は**存在するが一度もコンパイルされていない**
  （GLツールチェーンが環境に無い）
- `EntityBatcher` → `EntityBatchSet` まで CPU 側はできていて、`EntityCullRuntime.batches()` が
  生存者を渡せる状態になっている
- **そこから instanced draw を発行する経路が無い**

これが埋まれば 3 倍を超える。埋まらない限り CPU 側だけで 3 倍は出ない。

## このモデルの限界（正直に）

- 倍率が3シナリオで同じ(1.59×/2.91×)になっている。占有率モデルなので、
  TNT のような偏った負荷を表現できない。**C は実際にはもっと伸びるはず**で、
  前バージョンの絶対値モデルでは 3.63× だった。
- GPU 側の時間をモデル化していない。バニラが CPU 律速という前提。
- Mod先行率は各Modの公称機能からの推定で、実測ではない。
