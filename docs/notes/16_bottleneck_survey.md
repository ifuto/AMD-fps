# 16. ボトルネック調査と、最も重い 2 箇所の実装

**目的**: 「軽量 Mod 全入れの Fabric に、この Mod 単体で勝つ」ために、まず *どこが重いか* を
確定させる。
**制約**: この環境には Minecraft も GPU も無い。**実測は不可能**。したがってホットスポットは
推測ではなく、海外の論文・フォーラム・既存 Mod の第三者実測値から特定する。
**対象**: 全軽量化 Mod 全入れのベースライン = Sodium + Lithium + ImmediatelyFast +
EntityCulling + FerriteCore + ModernFix + Krypton + MoreCulling。
**ここに Nvidium は入らない**（NVIDIA 専用）。つまり AMD ユーザのベースラインには
GPU 駆動カリングが **一つも入っていない**。これが最大の空白。

---

## 1. ボトルネック順位（根拠付き）

Minecraft Java は **圧倒的に CPU バウンド**。フレームの段階は
`ゲームロジック同期 → チャンクメッシング(CPU) → カリング → ドローコール`。
Smooth Lighting はメッシュ時に焼き込まれるので、コストはリビルド時にしか出ない。

| 順位 | 箇所 | 第三者実測 | 全入れベースラインでの状態 |
|---|---|---|---|
| 1 | **チャンクリビルドのトリガ数** | **ブロック 1 個設置で `RenderChunk#rebuildChunk` が約 50 回**（Forge ユーザ実測）。内訳の大半は形状ではなく**リライト** | **誰も対策していない。** 統合(coalescing)を実装した Mod が見つからない |
| 2 | **遮蔽されていないエンティティ** | 石壁の向こうの牛 1000 頭: vanilla **24** / Sodium **45** / Sodium+EntityCulling **140+** FPS | EntityCulling が入るが、これは**空きコアでの CPU レイキャスト**。既に CPU バウンドのマシンでは逆に負ける |
| 3 | **immediate mode（マップ・文字・HUD・ブロックエンティティ）** | マップ 930 枚 +Sodium **47→320 (6.81×)**、牛 1000 頭 **16→60 (3.75×)**、看板 200 **110→300 (2.73×)**、チェスト 400 **315→410 (1.30×)**、HUD **335→630 (1.88×)** | ImmediatelyFast が入る。**CPU がボトルネックのときだけ効く** |
| 4 | **レンダー距離とチャンク数** | 8→16 でチャンク数 4 倍。16→12 で約 44% 減 | MoreCulling が入る |
| 5 | **TNT のラグ** | **大部分はクライアント側**。切断・再接続やレンダー距離外に出ると直る。サーバ側は `/tick entities tnt` に出る | Lithium の爆発最適化が入るが、クライアント側のリビルド嵐は残る |
| 6 | 三角関数テーブル | `Mth.SIN` は 65536 float = **256 KB** | 未対策（後述、保留） |

**TNT のラグは 1 と 5 の合成**である。爆発は 1 ティックで数百ブロックを変え、
その各々が最大 8 セクションを dirty にし、各 dirty がリライトでさらに広がる。

## 2. 実装した 2 箇所

### 2.1 リビルドの統合と、ライトだけを分ける（`net.amdfaster.dirty`）

**根拠**: 上記 1 位。約 50 回のリビルドの大半がリライトで、
**ライトデータが頂点データと同じバッファに入っているから**形状まで作り直される。

三段構成:

**(a) `SectionSet` — 正確な最小 dirty セット。**
ブロック変更が無効化するのは自分のセクション + **ローカル座標が 0 または 15 の軸ごとに 1 つの隣**。
1〜8 個（最悪 2×2×2）。

サンプル（x ∈ [-40,40), y ∈ [60,80), z ∈ [-40,40) の 128 000 ブロック）で実測した分布:

| 無効化されるセクション数 | 出現数 | 割合 |
|---|---|---|
| **1** | **83 300** | **65.1 %** |
| 2 | 38 500 | 30.1 % |
| 4 | 5 900 | 4.6 % |
| 8 | 300 | 0.2 % |
| 3, 5, 6, 7 | 0 | 各軸 1 か 2 の積なので 3 は原理的に出ない |

**vanilla は最悪の 8 を唯一の場合として扱う。65% は 1 で済む。**

**(b) `RebuildScheduler` — 2 つの dirty セットと重複排除。**
幾何とライトを別セットに持ち、幾何がライトを包含する
（幾何リビルドはライトも再計算するので、両方残すとライトストリームを 2 回アップロードする）。
1 フレームのバジェット内で、種類ごとに近さ順（線形距離の 32 バンドで counting sort）。
残りは pending のまま。

**バンドを距離の 2 乗にしなかった理由**: 2 乗の方が安いが形が違う。
256 ブロックのレンジで 2 乗バンドにすると最初のバンドが距離 8 ブロック分、
最後が 32 ブロック分を覆い、**カメラから 8 ブロック以内のセクションが全部 band 0 に潰れて
ハッシュ順に吐かれる**。それはまさに玩家が見ているセクション。sqrt の数ナノ秒は払う。

**(c) ライトだけを分ける意味。**
Stage 9 でライトを独立した頂点ストリームにした（`LIGHT_BYTES_PER_MESHLET=992` /
meshlet あたり 5332 バイト = **18.6 %**）。だからライトのみの変更は
**そのストリームだけを書き換えればよく、greedy meshing と AO を丸ごと飛ばせる**。
interleaved なレイアウトでは 1 頂点 1 ワードのために全部書き直すことになり、
**だから interleaved なレンダラではこの最適化が原理的にできない**。

**ドレイン順は load-bearing。** ドレインされたセクションはメッシュを**作る前**に
pending から外す。後で外すと、ビルド中に来たブロック変更がセクションごと捨てられ、
**何か別のことがそのセクションを dirty にするまで直らない穴**が残る。

### 2.2 エンティティの遮蔽カリング（`cull/PyramidGeometry`, `cull/CameraCutDetector`,
### `entity/EntityOcclusionCuller`, `shaders/entity_occlusion.comp`, `shaders/hiz_reduce.comp`）

**根拠**: 上記 2 位。EntityCulling は CPU レイキャストなので、
**CPU バウンドのマシンでは勝てない場合がある**。深度ピラミッドは地形パスが既に作っているので、
エンティティ 1 個につき適切なレベルの 1 フェッチで答えが出る。

**ピラミッドは地形だけから作る**（エンティティは depth を書かない）。
書くと、前フレームに可視だったエンティティが自分の深度を残し、
今フレームの位置と前フレームの位置を比べることになる。
**遠ざかると自分の古い深度の下に落ちて culled → 描画されない → 次フレームの
ピラミッドにも居ない → 二度と戻らない。** これは bias や epsilon では直らない構造問題。
代償としてエンティティ同士は遮蔽し合わないが、それは他のエンティティカラーも同じで、
正しさを賭ける価値はない。

## 3. 既存コードで見つかった 3 つの実バグ

`meshlet_occlusion.comp` を精読して見つかったもの。**3 つとも「カリングを逃す」のではなく
「可視の幾何を消す」方向の誤り**。

### 3.1 reduction が max だった（重大）

reversed-Z では大きいほど手前。「完全に隠れている」=
**box の最近点が footprint の全サーフェスの後ろ** = footprint 上の **最小** 深度との比較。

max は別の質問に答えている:「この領域のどこかにある最近点より後ろか」。
**領域内に手前ピクセルが 1 つあれば成立してしまう。**

```
サーフェス深度 [0.9, 0.9, 0.05]、box の最近点 0.4
  MAX → 0.90 判定 0.4 < 0.90 = true → CULL  （誤。box は 0.05 のピクセルから見えている）
  MIN → 0.05 判定 0.4 < 0.05 = false → 残す （正）
```

これがテストの判別器になっている: **footprint がピクセル 512 で壁の境界をまたぐ
エンティティ**は、min なら残り max なら消える。

### 3.2 box 中心の 1 テクセルしか読んでいなかった

box は中心テクセルからはみ出す。中心だけを読むと **自分のものではない footprint に対して
判定する**。選択レベルでは box は 1 軸あたり高々 2 テクセルなので、
全域を歩いても高々 4 フェッチ。両パスとも span 全体を読むようにした。

### 3.3 ピラミッドが floor 半分だった

Vulkan は mip n を `max(1, dim >> n)` と定義する（切り捨て）。
1920×1080 では **level 4 が 67 行**になり、67×2 = 134 なので
**level 3 の 135 行目は上位のどのテクセルにも属さない**。1080p から 1×1 の間に
こういうレベルが **5 つ**ある。

ceil 半分にし、reduction の範囲外 tap は端にクランプする。
クランプは既に reduction に含まれる値を 2 回読むだけなので、**min の結果は変わらない**。

**599 の基底サイズ × 20 レベルで網羅検証**:

| 方式 | テクセルを取りこぼすステップ数 |
|---|---|
| ceil 半分 + クランプ tap | **0** |
| Vulkan の floor 半分 | **2 061** |

1920×1080 のチェーン（ceil）:
`1920×1080 → 960×540 → 480×270 → 240×135 → 120×**68** → 60×34 → 30×17 → 15×9 → 8×5 → 4×3 → 2×2 → 1×1`
（floor なら level 4 は 120×**67**）

**これは reduction を min に直した瞬間に正しさの問題になった。**
取りこぼしは max reduction では値を*小さく*する（=カリングを逃すだけ）が、
min reduction では値を*大きく*する（=**可視の幾何を消す**）。

### 3.4 `hiz_reduce.comp` が存在しなかった

2 パスカリングの前提であるピラミッド生成シェーダが**そもそも無かった**。
`workgroup 8×8 = 64`（RDNA の wave サイズ丁度）。
`VK_EXT_sampler_filter_minmax` があれば bilinear 1 tap で済むが、
明示 4 フェッチが移植可能な形。

## 4. カメラカット検出（`CameraCutDetector`）

2 パス方式は前フレームの深度を再利用することで成り立っており、
**その再利用が壊れる条件がある**。エンダーパール、`/tp`、リスポーン、
ディメンション移動、速いマウス操作。

これに対して古い深度でカリングすると、**culled された幾何は再描画されないので
次のピラミッドにも入らず、誤りが自己修正されない**。これがオクルージョンカリングを
オフにさせるあのアーティファクトで、原因はどのパスのバグでもなく**古い入力**。

| 定数 | 値 | 根拠 |
|---|---|---|
| `POSITION_JUMP_BLOCKS` | 8.0 | スプリントでも 6 blocks/s、60fps なら 0.1 block。長い落下は**意図的に**カット扱い（洞窟に落ちたとき地表のピラミッドで洞窟の床を culled してしまう） |
| `ANGLE_JUMP_RADIANS` | π/4 | 1 フレームで 45° は首を振ったのではなく鞭を打った |
| `RECOVERY_FRAMES` | 2 | 1 フレームでは足りない。カットの次のフレームが prepass ピラミッドで culled される最初のフレームで、1 フレームの過剰カリングが次のピラミッドに穴を残す |

**Minecraft の yaw は無限に累積する**ので角度差は wrap する。
生で比べると **2π の倍数を跨ぐたびにカットを報告し、たまたま正しい向きを向いている
玩家はオクルージョンカリングが永久に効かない**。
`wrappedDelta` は [0, π] を返し、a,b ∈ [-20,20] を 0.37/0.53 刻みで全走査して範囲を検証。

## 5. 調査したが保留したもの

### 三角関数テーブル（**数値を訂正**）

`Mth.SIN` は 65536 float = **256 KB**。L1/L2 に収まらないテーブルは
ランダムインデックスのミスが他のデータを追い出すので、**計算するより遅くなりうる**
（Forge フォーラムの実測で 65536 エントリと 1024 エントリが同速、
Stack Overflow / GameDev の一般論も同様）。

1024 エントリ + **線形補間**なら:

| | サイズ | 最大誤差 |
|---|---|---|
| 65536 エントリ、最近傍 | 256 KB | π/65536 = **4.79e-5** |
| **1024 エントリ、線形補間** | **4 KB** | h²/8, h = 2π/1024 → **4.71e-6** |

**10.2 倍小さく、かつ 10.2 倍正確**（以前この値を「64 倍」と書いたが誤り。
64 倍は *エントリ数* の比で、誤差の比ではない）。

**保留の理由**: `src/main/java` で `Math.sin`/`Math.cos` を呼ぶ箇所が**一つも無い**
（`Math.sqrt` のみ）。呼び出し元の無いテーブルを置けば、それは禁止された
「未接続の実装」そのもの。`Mth` への mixin として入れれば本物だが、
それは Minecraft クラスへのグローバルな差し替えで、
効果は上位 5 項目に比べて小さい。**上位が片付いてから。**
