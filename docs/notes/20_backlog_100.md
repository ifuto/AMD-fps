# 20. 実装バックログ 100 項目 — 状態管理

ユーザー提供の 100 項目候補を、**このリポジトリの実際の状態と突き合わせた**ToDo。
「忘れないように」が要件なので、このファイルが唯一の台帳。
実装したら状態と場所を更新する。**推測で状態を書かない** — 全て grep で確認した結果。

状態の意味:
- **完了** = 実装済みでテストがある
- **部分** = 一部だけ実装、または設計だけでコードが無い
- **未** = 何も無い
- **対象外** = クライアント側 Mod という制約、または Vulkan 優先という決定と両立しない

## 実装順（ユーザー指定のフェーズに従う）

### フェーズ 1：測定基盤と描画の土台
**100 → 2 → 3〜8 → 10〜15 → 21〜26**

- **100（計測）が最初。** これが無いと他の全ての効果主張が根拠を持たない。
  実際、これまで「実装したが測れない」を何度も書いてきた。
- 10〜15, 21〜26 は完了済みが多いので、残るは **3〜8（転送とディスパッチ）**。
  特に **1（ディスパッチ層）** が無いと GPU 側が一切動かない。

### フェーズ 2：描画以外の軽量化
**41〜55（光）→ 56〜75 のクライアント側 → 76〜90**

光エンジンが丸ごと無いのが最大の欠落。Starlight の技術資料が参照できる。

### フェーズ 3：AMD 固有の高度な経路
**23〜25 → 38〜40 → 91〜99**

## 比較の基準（ユーザー指定）

平均 FPS だけでなく **1% Low・フレーム時間のばらつき・チャンク再構築時間・RAM 使用量・GPU 実行時間**。
比較対象は Sodium 単体ではなく
**Sodium ＋ ImmediatelyFast ＋ EntityCulling ＋ Lithium ＋ FerriteCore ＋ ModernFix** の同バージョン構成。

この要件は項目 100 の設計に直接効く: 計測器は平均値だけでなく分位数とばらつきを出さなければならない。

## 注意（ユーザー指定）

論文の高速化率を Minecraft にそのまま当てはめない。
元の実験で速かった処理が、Minecraft では CPU・メモリ転送・ドライバーの別のボトルネックで
逆効果になる場合がある。**測ってから入れる。**
